# СМ-Клиника: не потерять пациента

Прототип системы, которая читает протокол УЗИ, находит в нём клинически значимые
изменения и запускает следующий шаг маршрута — от записи к специалисту до
контрольного визита. Пациенту при этом уходит нейтральное уведомление, без диагноза.

## Зачем это нужно

После исследования человек получает заключение, и дальше всё зависит от того,
понял ли он результат и вернулся ли к врачу. Значимая находка часто так и остаётся
в тексте протокола, а между диагностикой и лечением образуется разрыв.

Мы не пытаемся заменить врача и не ставим диагноз. Задача узкая: распознать триггер
и организовать следующий безопасный шаг, чтобы пациент не пропал между этапами.

## Что уже работает

Протокол можно загрузить как .docx или .txt — система разбирает его и показывает
находки с цитатой из текста. Сейчас в справочнике 47 типов изменений: образования и
кисты, полипы, узлы, конкременты, аденомиоз, варикоз, изменения печени, поджелудочной,
щитовидной, молочной и предстательной желез и другие.

Разбор текста не сводится к поиску слов. Мы учитываем падежи («узл**ы**», «кист**ы**»),
привязку к органу, размеры, сторону (правая/левая), категории BI-RADS и TI-RADS.
Отдельно обрабатываем отрицания: «конкременты не выявлены» или «без признаков полипа»
находкой не считаются, а вот «миома без признаков роста» — считается, потому что
отрицается рост, а не сама миома. Формулировка «нельзя исключить» мы относим к
триггерам: на приёме врач разберётся.

По каждой находке видно, на основании чего она найдена, и какое правило сработало —
это важно и для врача, и для проверки качества.

Дальше система строит маршрут. Госпитализация нужна не всем, поэтому маршрут
ветвится: хирургический проходит через направление, госпитализацию и операцию,
консервативный заканчивается контрольным визитом. Приоритет тоже выставляется
правилами — экстренно, срочно, планово или наблюдение; BI-RADS 4 и выше автоматически
поднимается до «срочно».

Для координатора есть очередь маршрутов с фильтрами и сортировкой по срочности,
карточка пациента с этапами, журналом событий и откатом статуса, а также разделы
«Требует уточнения» и «Без клинических значимых триггеров». Последний нужен, чтобы
ни один протокол не потерялся, даже если в нём ничего значимого не было.

Пациенту уходит текст примерно такого вида: «В заключении описаны изменения, по
которым рекомендуется консультация профильного специалиста». Диагноза там нет.
Если находок несколько, сообщение всё равно одно — чтобы не заваливать человека
пушами.

## Как устроено

Код разделён на три части.

Ядро (`app/processor.py`) отвечает только за разбор текста: находит изменения,
определяет сторону и атрибуты, помечает отрицания. Решение о маршруте принимает
не оно, а матрица правил в `rules/routing.json` — так извлечение фактов отделено
от логики направления.

Маршруты, статусы, очередь уточнения и модельное время живут в `web/store.py`.
Правила распознавания лежат в `rules/triggers.json`, список формулировок-
неопределённостей и исключения для отрицаний — в `rules/uncertainty.json`.

Интерфейс написан на React и собирается в `frontend/dist`. Сервер FastAPI отдаёт
и его, и API — отдельный веб-сервер не нужен.

```
sm_case/
├─ start.bat            запуск в один клик
├─ requirements.txt     зависимости Python
├─ app/processor.py     разбор протокола
├─ app/anonymize.py     обезличивание ФИО
├─ app/llm_extractor.py локальная LLM (shadow-режим)
├─ web/app.py           API и отдача интерфейса
├─ web/store.py         маршруты, статусы, действия
├─ frontend/            интерфейс (src — исходники, dist — сборка)
├─ rules/               правила: находки, маршруты, неопределённость
├─ docs/                контракт данных
├─ schemas/             JSON-схема разметки
├─ scripts/             прогон, метрики, аудит, утилиты
└─ materials/protocols/ протоколы для демонстрации
```

## Запуск

Нужен только Python 3.11 или новее (у нас стоит 3.13). Node.js не требуется —
интерфейс уже собран и лежит в `frontend/dist`.

```
cd C:\Users\alina\Documents\Default Project\sm_case
pip install -r requirements.txt
start.bat
```

Откроется адрес http://127.0.0.1:8000 — там и интерфейс, и API. Если окно с
сервером закрыть, сайт перестанет отвечать; чтобы остановить вручную, нажмите
Ctrl+C в этом окне.

То же самое без bat-файла:

```
python -m uvicorn web.app:app --host 127.0.0.1 --port 8000
```

Интерфейс меняется редко, но если нужно править его, потребуется Node.js. В этом
случае запускаем отдельный сервер разработки — правки подхватываются сразу:

```
cd frontend
npm.cmd install
npm.cmd run dev
```

Он откроется на http://127.0.0.1:5173 и будет проксировать запросы к основному
серверу на порту 8000, поэтому FastAPI тоже должен быть запущен. После правок
собрать версию для основного адреса:

```
npm.cmd run build
```

## Роли, вход и выбор врача

При открытии http://127.0.0.1:8000 появляется экран входа. Там выбирается роль, а
для профильного врача — ещё и специальность; имя можно не указывать. Выбор
сохраняется в браузере, кнопка «Сменить» в шапке возвращает к экрану входа.

Важно: конкретного врача пациенту вручную не назначают. Специальность определяет
матрица правил `rules/routing.json` по найденной находке — координатор только
подтверждает и двигает маршрут. Поэтому «выбор врача» на экране входа — это выбор
роли, под которой вы смотрите систему.

| Роль | Что видно в системе |
|---|---|
| Главный врач | Всё: маршруты, уточнения, норму и статистику |
| Координатор | Полную очередь маршрутов и все действия |
| Профильный врач | Только пациентов своей специальности (выбирается на входе) |
| Хирург | Только хирургические маршруты, начиная с этапа «Врач определил тактику» |
| Онколог | Только маршруты с явным онкологическим направлением |

Фильтрация выполняется на сервере, а не в интерфейсе: в ответ API попадают только
разрешённые маршруты. Роль передаётся в запросе
`GET /api/routes?role=…` (для профильного врача — ещё `&specialty=…`).

Где видно специальность:

- в очереди слева — справа от номера пациента;
- в карточке, блок «Рекомендованный маршрут» — специалист и следующий шаг;
- фильтр «Все специальности» над очередью доступен главному врачу и координатору
  и сужает выборку;
- у профильного врача специальность зафиксирована на входе; у хирурга и онколога
  список формируется автоматически по этапу маршрута и направлению.

## Откат статуса и история

Любой этап можно вернуть на предыдущий — кнопкой «↶ Вернуть предыдущий этап»
рядом с текущим статусом.

- Откат выполняется на сервере (`POST /api/routes/{id}/rollback`) и сразу
  пересчитывает текущий этап, доступность следующих кнопок, статистику и воронку.
- Перед откатом показывается подтверждение. Если после текущего этапа уже были
  выполнены более поздние — они перечисляются в предупреждении, и откат отменяет
  их вместе с текущим. Молча «сломать» последовательность нельзя.
- История не стирается: откат добавляет новое событие. Для каждого изменения
  хранятся `previous_status`, `new_status`, время, роль пользователя и тип
  действия (`status_changed` или `status_rollback`).

```
Было:   Записан → Приём состоялся
Откат:  Приём состоялся → Записан
        (оба события остаются в «Истории событий»)
```

## Про данные

Протоколы обезличиваются на входе: ФИО пациента скрывается до анализа и до
сохранения, в системе оно не остаётся. По вашему решению остальные поля не
трогаем.

Сервер слушает только 127.0.0.1 и никуда не обращается — работает без интернета,
данные не покидают машину. Хранится минимум: обезличенный идентификатор, текст
протокола и находки. В уведомлении пациенту диагноза нет.

Отдельно стоит сказать про очередь «Требует уточнения». Туда попадают протоколы
двух видов: совсем непонятные (нет ни заключения, ни диагноза, ни рекомендации) и
те, где находка описана в тексте, но не вынесена в заключение. Если таких
расхождений становится больше 5%, система перестаёт их помечать — это защита от
шума. Патологические заключения и «нельзя исключить» в эту очередь не попадают:
по ним маршрут создаётся сразу.

## Пациентские сценарии

Сейчас реализовано пять.

Первый — обычный: пациент получил уведомление, записался, пришёл, врач определил
тактику, дальше либо госпитализация с операцией, либо контрольный визит.

Второй — человек не реагирует. Ему напоминают через сутки и через трое, затем
координатор звонит, а через месяц маршрут помечается как нереализованный.

Третий — неявка: после отметки система предлагает перезаписаться и возвращает
пациента к шагу записи.

Четвёртый — несколько находок в одном протоколе. Сообщение пациенту уходит одно,
а маршруты ведутся по каждому изменению.

Пятый — норма. Уведомление не отправляется, протокол просто сохраняется.

Доступа к МИС, расписанию и личному кабинету у нас нет, поэтому запись, SMS и
push имитируются. Формат обмена описан в `docs/api_contract.md` — по нему
подключается реальная система.

## Локальная LLM (Qwen3-8B)

Рядом с правилами можно включить локальную модель — как **дополнительный** источник
извлечения фактов. Она не ставит диагноз, не выбирает врача и не строит маршрут:
маршрутизация целиком остаётся на детерминированных правилах. Модель отвечает
только на вопрос «что фактически написано в протоколе».

По умолчанию выключена, проект работает и без неё.

1. Установить Ollama: https://ollama.com
2. Скачать модель:
   ```
   ollama pull qwen3:8b
   ```
3. Проверить:
   ```
   ollama run qwen3:8b
   ```
4. Включить в проекте переменными окружения:
   ```
   USE_LLM=true
   LLM_MODE=shadow
   OLLAMA_HOST=http://127.0.0.1:11434
   OLLAMA_MODEL=qwen3:8b
   LLM_TIMEOUT_SECONDS=30
   ```
5. Запустить проект обычным способом.

Состояние модели — `GET /api/llm/status`. В интерфейсе, когда модель включена,
в шапке появляется плашка «LLM: qwen3:8b · локально».

Режим `shadow` означает: результат модели сохраняется рядом с правилами для
сравнения, но **не влияет** на маршрут, приоритет и специалиста. Если Ollama не
запущена, модель не скачана или случился таймаут — система молча продолжает
работу на правилах, ошибка только пишется в журнал. В логи не попадают ни текст
протокола, ни персональные данные — только идентификатор исследования, модель,
время ответа и число находок.

Сравнить результаты модели и правил можно скриптом:
```
python scripts/evaluate_llm.py
```
